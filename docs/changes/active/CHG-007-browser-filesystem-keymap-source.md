## Acceptance criteria

- Supported secure-context browsers can explicitly select one existing raw `.keymap` and save only that file through File System Access without GitHub or a Node filesystem service. Folder selection is read-only discovery. Every Save, through either entry route, requires a fresh explicit Save-access action to reselect the exact firmware file through a file picker and prove `isSameEntry`; directory-route Save additionally proves the current exact directory entry. Unsupported browsers retain Clipboard with clear guidance.
- Cancellation, permission denial/revocation, vanished files, external modification, write failure and lost browser handles preserve the draft and do not falsely report Saved. No automatic permission prompts on startup.
- Confirm file identity and baseline before write; preserve source via shared core serialization. The approved scope of this entire CHG is one existing raw `.keymap` output per Save, not multi-file publication. Reject all extra outputs before opening a stream; the non-atomic multi-file protocol below specifies deferred future work only.
- Optional geometry is read-only and must pass adapter-side `validateInfoJson` before `loadKeyboardBundle`. Sidecar, geometry and host writes are deferred beyond this CHG; disclose that they are not written. ADR 0002/0005 repository-root paths are not browser write targets under a config-directory grant. Never request directory-wide write access.
- Browser handles stay browser-local if persisted, require permission revalidation, and never leak through GitHub commits or host snapshots.

### Proposed scope decision

Everything below specifies proposed behavior, not implemented behavior or passing test evidence. The approved scope for **all phases of this CHG** is a **raw `.keymap`, firmware-only adapter**: file and directory entry routes select one existing firmware file; each Save writes that file only. References to the first slice mean this bounded CHG, not a later multi-file phase within it. Directory selection is read-only discovery, not write authorization or permission to synchronize a repository. Multiple firmware files can be edited in separate identity-scoped sessions, never as a batch Save.

**Per-attempt Save authorization (both routes):** Open/restore/reconnect handles identify the document but do not authorize a later Save. Each Save attempt, including a retry or a second Save after success, starts with a fresh user-activated `showOpenFilePicker` selection of exactly one existing `.keymap`. Prove `isSameEntry` with the accepted document handle before requesting write permission; directory mode also resolves and proves its exact direct entry. Bind the fresh picked handle and proof to that document, session generation and attempt only. Cancellation, denial, failure, completion or a superseding session invalidates that attempt's authorization; a remembered handle or prior granted permission cannot skip reselection. A later explicit Grant access gesture may continue the same attempt, but identity and byte preflight must run again afterward. Only that attempt's proved file-picker handle may open the stream. An uncertain-attempt reconciliation also requires fresh identity proof, even when intended bytes are already present and no rewrite is needed.

Directory listing order is the exact filename's JavaScript UTF-16 code-unit order (`a < b` / `a > b`), independent of locale and enumeration order. Preserve spelling/case; do not normalize names into identities.

- **Open file** uses `showOpenFilePicker` with one `.keymap` selection. Validate the returned file rather than trusting the picker filter; reject templates, JSON-only input, empty/invalid firmware and non-file handles. Stage valid firmware without replacing the accepted session. Offer **Choose layout JSON** as a separate later explicit action with fresh user activation, or **Open without layout** to opt into inference; never chain a second picker after the `.keymap` picker resolves. Layout-picker cancel keeps that staged firmware candidate and the old accepted session/layout unchanged; invalid/unreadable supplied geometry also refuses candidate acceptance, not silently opening without layout. The user may retry layout selection, explicitly open without layout, or cancel the candidate. Do not infer siblings or ask for a directory to make file mode work.
- **Open folder** uses `showDirectoryPicker` in read mode. Ask for the directory directly containing keymaps (for a typical checkout, its `config` directory). Enumerate direct entries only, list eligible files using core `isUserKeymapFilename`, sort exact names deterministically, then require an explicit file choice even for one candidate. Do not recurse, traverse parents, follow includes, select a parent, create directories, or silently choose another file if the remembered selection vanishes. Empty or failed enumeration leaves the accepted session intact; failed enumeration is not an empty inventory. The directory and its derived child handles remain discovery/read inputs only. For **each Save**, a fresh explicit **Save access: select this .keymap** action must open `showOpenFilePicker` and acquire a separate handle for the exact existing firmware file. Prove `isSameEntry` against the accepted discovery handle and the current exact directory entry before write permission or stream creation. Cancellation, wrong selection or failed proof preserves the candidate/session/draft and writes nothing. Never request readwrite on the directory or its derived child handle; do not assume a child grant narrows an ancestor's write permission. Only the separately picked, proved-equivalent file handle may be used for Save. If file picking is unavailable, folder discovery is read-only even if a child exposes `createWritable`.
- Geometry is optional and read-only: directory mode may use the selected file's matching `<stem>.json` from core `matchingInfoJsonFilename` only after an additional adapter-side collision exclusion. The helper does not reject every firmware-sidecar name: `foo.keymap.keymap` returns `foo.keymap.json`; exclude this `.keymap.json` result rather than reading it as layout. Never automatically use shared `info.json`, `keymap.json` or any firmware JSON as geometry. File-mode explicit selection may associate an `info.json` with this session only, but may not import firmware sidecars as geometry. For **every supplied geometry input**, parse JSON and call core `validateInfoJson` in the adapter **before** `loadKeyboardBundle`; do not rely on the bundle loader to reject non-layout JSON. Only missing/unselected/excluded geometry is absence and may infer with a warning. Invalid JSON, `null`, `{}`, `{ "layouts": {} }`, firmware-shaped JSON or inaccessible supplied geometry refuses the candidate load: no inferred fallback and no accepted new session. A missing optional matching file at initial discovery is absence; disappearance of an already captured dependency is a Save failure. No geometry file is written.
- DTS is the only firmware input and the accepted original source for `buildKeymapCode`. Do not read or write `keymap.json`, `<full-keymap-filename>.json`, templates, mode markers, host snapshots or install files in this slice. Core necessarily computes a returned `json` alongside `code`; ignore that value, do not persist/export it as a filesystem output, and do not alter the shared writer to suppress it. A directory inventory can disclose ignored sidecar names without reading their contents. Show that this is raw-file editing: other tools, including GitHub's JSON-first load, may still read an unchanged sidecar instead. File-only access cannot establish whether siblings exist; do not claim they are absent or synchronized.
- [CHG-004](../archive/CHG-004-select-keymap-file-within-repository.md), [ADR 0002](../../adr/0002-keymap-file-contract.md#chg-004-amendment--selected-github-file-ownership) and [ADR 0005](../../adr/0005-host-keymap-github-snapshot.md#chg-004-amendment--owned-snapshots-and-safe-omission) remain authoritative for selected GitHub files. Their marker/pinned-tree ownership proof is not established by a browser directory grant or by a matching filename. Reuse their identity-isolation and no-guessing principles, not GitHub mode inference or server write authorization. No legacy adoption, marker creation/migration, sidecar replacement or host omission/discard flow is imported into this source.
- ADR 0002/0005 paths are repository-root contracts for GitHub, **not a browser expansion write set**. A grant for `config` neither identifies/proves the repository root nor permits parent traversal to a sibling host tree. Directory discovery may enumerate only direct entries; it cannot claim to inventory repository-root markers or host artifacts outside that directory. Future sidecar/host support needs a separately approved scope proving root selection, permissions and ownership before proposing any browser output paths. No such model or output set is specified here. Shared/other-file artifacts remain untouched; matching names and invalid or ambiguous host state never authorize replacement. Do not implement a multi-file engine in any phase of this CHG.
- Host profiles/legends remain browser-local under the existing non-GitHub contract. The save action and receipt must say **Save .keymap** / **Firmware saved; host files not written**, not generic all-work Saved. Filesystem chrome/status/receipts must never fall through to generic **Saved**, **Up to date with disk**, or GitHub **Commit** wording. Clean open must identify loaded firmware, not claim a save; host-only edits must remain explicitly browser-local; verified firmware Save must disclose host files not written; pending recovery must remain explicit even with a clean visible model. All four states must disclose the firmware-only scope and that host files are not written. Linux/Windows downloads remain separate Host-lane actions and do not become filesystem Save or OS installation. No handle is needed for those existing downloads.
- Save As, file creation, deletion/rename, template-backed generation, JSON-only import, automatic merge/force overwrite, batch saves, filesystem watchers and expanding macro/behavior/layer authoring eligibility are outside this first slice. Existing core editing restrictions remain in force; a new source must not be mislabeled Clipboard to unlock them. Clipboard remains the explicit manual escape route, not an automatic write fallback.

### Identity, baseline and completion vocabulary

The proposed browser source needs its own discriminator and versioned opaque filesystem document ID in the **actual editor draft identity and draft store**, not merely an adapter-side handle map. Extend `DraftIdentityInput`, `DraftIdentity`, `buildDraftIdentity`, `draftIdentityKey`, `StoredDraft`, `currentDraftIdentity` and selection payload/state plumbing for that ID. It must participate in every load/save/delete/restore/transition key and revision guard; do not hide it in `keyboard` or GitHub `keymapPath`, or reuse `local`, `clipboard`, a GitHub identity or a basename. These are required future extensions, not fields/types already implemented.

- **Document identity:** an origin-local record associated with an actual file handle. Use `isSameEntry` to prove equivalence when comparing freshly selected/restored handles, including opening the same file through different routes. Same name, contents, size or modification time never proves identity. Keep the directory grant and exact relative entry name as route context, not an absolute OS path or global file ID. Before a directory-route Save, reselect through the separate file picker, resolve that exact direct entry again without creation and prove all handles identify the accepted file; replacement, failed proof or disappearance blocks writing through a stale handle. Repeat directory-entry identity checks at pre-stream and readback boundaries; never write using the directory-derived child. File-only mode can check only its granted handle, not inaccessible parent-directory identity.
- **File baseline:** persist the exact bytes read from the accepted file, its verified original source text, parsed firmware, layout and source/history metadata under the filesystem document ID, separately from the mutable draft/working source and save-attempt recovery. Do not rely on Clipboard session storage or identity-aware layer metadata being present to retain the original source. Clean draft retirement must not delete this verified baseline/source record. Decode supported UTF-8 without silently replacing invalid bytes; refuse unsupported input before accepting it. Byte comparison (or a digest over all bytes) is authoritative for external-change detection; size and `lastModified` are diagnostic hints only. Do not trim, normalize line endings or compare only parsed bindings to declare a file unchanged. The saved bytes are UTF-8 of core's complete `code`, with source-preservation behavior owned by core, not a second browser formatter.
- **Read dependencies:** any selected geometry handle and bytes also belong to the captured baseline. Re-read them before Save; a changed/missing/unreadable dependency blocks Save rather than silently changing layout, dropping the dependency or falling back to inferred geometry. Ignored sidecars are not read dependencies and receive no freshness guarantee.
- **Save attempt:** capture document identity, session generation, exact sent draft, source, layout and history/layer metadata before asynchronous work. Validate/build with core before opening a writable stream. Retain and verify the captured draft, original baseline and intended output in identity-scoped browser recovery before writing; failure refuses Save without opening a stream. This recovery record contains no handle and is separate from opt-in handle retention. Revalidate permission, identity and fresh file/dependency bytes after any permission prompt and immediately before opening that stream. One attempt per accepted document at a time; double clicks do not start competing writes.
- **Verified completion:** `write()` resolving is insufficient. Require successful `close()`, then a fresh `getFile()` and full-byte equality with the captured output, with directory identity checked again where available. Only a dedicated filesystem receipt path can accept the sent firmware baseline; never route this source through `publishKeymap` or `applyPublished`. Persist the verified disk bytes/source and matching model as the next original baseline separately from newer working source, before retiring matching recovery. The stored firmware model must remain a fresh parse of those exact bytes: editor layer names must not overwrite source-derived `layer_names` (RF01 below). Validate the replacement baseline with the same invariant used on reopen before committing it. Persistence failure leaves recovery protected and blocks further writes; do not claim recovery retirement succeeded merely because disk readback did. Newer edits remain dirty; a superseded session cannot update another session's baseline, notice, history or saving lock. A second Save, including after restore, must splice against that verified original source, never `default_template`. If reconciliation cannot preserve newer edits and source provenance, keep recovery and refuse further writes rather than rebasing silently. No host-baseline acceptance or GitHub host-omission calls belong to this path.
- **Uncertain completion:** a failed close or post-close read is not proof that disk stayed unchanged. Retain original baseline, intended bytes and draft; show **Save not verified; file may have changed**. No automatic retry/rollback. A later explicit retry first reads the same entry: original bytes allow a new attempt; exact intended bytes allow reconciliation of the captured attempt without rewriting; anything else is a conflict. Reconciliation after a failed close must explicitly confirm the observed intended result, not retroactively claim the failed call succeeded.
- **Interrupted preparation and recovery retirement:** retaining a pre-stream journal is required, but it is not evidence that a writable was opened. Persist preparation versus possible-write state before invoking `createWritable`; a crash in that gap remains conservative. Successful guarded retirement of the exact attempt permits an editable retry; failed retirement keeps pending protection and an explicit storage-recovery notice. Never derive pending solely from an in-memory `writeStarted` flag. After reload, Restore restores the draft only; an explicit same-entry, full-byte reconciliation must resolve surviving attempts, including legacy attempts without a stage. Original bytes permit guarded retirement without baseline adoption, intended bytes permit explicitly confirmed receipt reconciliation without rewriting, and third-value/unreadable inputs remain protected. RF02 specifies the transitions and UI handoff.
- **Race limit:** File System Access does not provide an app-level compare-and-swap against external editors. Pre-write and post-close checks detect observed changes, not every concurrent write between those checks or after verification. Do not promise GitHub head-SHA safety, a filesystem lock, atomic directory saves or crash durability. Encourage one writer; never “resolve” an observed conflict by automatic overwrite.

### Current-source grounding and required seam changes

### Non-atomic multi-file extension boundary

This entire CHG deliberately avoids partial multi-output Save by refusing it (S15); opening a folder does not relax that rule. This does not claim the original multi-file risk has been solved by an atomic API. The following is a future protocol only, not a Phase 2–4 deliverable or authorization of any browser output path. A separate scope must first prove its root/permissions/ownership model; ADR repository-root paths and a config-directory grant do not supply one:

1. Freeze and show the exact ordered output set, each proven owner/handle, original bytes (or proved absence for separately authorized creation), and intended bytes. Build all outputs with core and preflight all identities, permissions, baselines and read dependencies before the first write. A failure at preflight writes nothing. Any scope change invalidates consent.
2. Keep an identity-scoped browser-local attempt record before the first write; if it cannot be retained, refuse the multi-file attempt. Write sequentially, recheck each target just before its write, and close/read back each file. Stop at the first failure or conflict. Completion states are **not attempted**, **verified written**, and **unverified/failed**; exceptions after writing cannot be relabeled unchanged. Persist receipts as each completes, without promising that an IndexedDB transaction is atomic with disk.
3. If output A is verified and B fails, disclose A's completion, B's uncertainty and C's not-attempted status by exact target. Retain the full draft/attempt and leave aggregate publication pending; do not advance an all-files baseline, claim host delivery or roll A back automatically. A failed rollback could overwrite somebody else's edit and would be another non-atomic write.
4. Explicit retry/reopen re-reads **every** target, including previously verified outputs. Intended bytes may be reconciled as already present; original bytes remain eligible for a new confirmed attempt; any third value, missing expected file, inaccessible handle or changed identity stops for conflict/reconnect. A crash can occur between close and journal persistence, so the journal alone is never proof. Lost journal/handles cannot justify blind continuation. Retain recoverable text and offer manual reconciliation instead.
5. Report aggregate completion only when all required outputs from the same captured attempt have verified receipts; never accept newer live edits. Firmware/host results stay distinct, and optional omissions must be named. These predicates are review oracles for future multi-file tests, not a requirement to create a generic writer in this change's first slice.
