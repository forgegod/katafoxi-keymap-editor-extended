This active CHG-004 is the sole implementation-progress authority for this request. Direct operator request:

1. Same-keymap Reload is never a discard affordance.
2. Incompatible/unsupported remote host snapshots need an explicit destructive "Discard local host edits" path.
3. That action discards host edits only, never publishable firmware drafts.
4. While remote snapshot writing is omitted, host edits remain usable but are explicitly browser-local and unpublishable.
5. Resequence the active CHG before implementation; do not continue patching the unintegrated candidate archive.

Required recovery contract for implementation:

- Same-keymap Reload is non-destructive in all states and preserves recovery for both firmware drafts and local host edits. It cannot be described as discard, clear a recovery block by deleting work, or be recommended as a destructive exit.
- An existing host-recovery block means an invalid/incompatible or unsupported remote host snapshot plus local browser-host edits while remote host writes are omitted. Provide an explicit destructive **Discard local host edits** action to clear that block, available even in a single-keymap repository without choosing another GitHub destination. Its confirmation must name the selected repository/branch/keymap's browser-local host edits and associated host recovery state being removed, explain the resulting host state, and state that firmware drafts and remote files are unchanged. Unrelated identities and browser host profiles outside that named scope must remain intact.
- Require confirmation before discarding any host state; cancellation changes nothing. Only when the host-recovery block defined above exists is successful confirmed host-only discard required to clear it before a requested source/repository/branch/keymap change, subject to independent firmware protection. Host-only discard is not a universal transition prerequisite: never require it for clean transitions or after a compatible host snapshot has successfully published. Preserve live and stored publishable firmware drafts; host-discard consent is never firmware-discard consent. Remaining firmware work must be published or safely retained under its original identity before switching, or separately discarded with explicit firmware consent.
- While remote snapshot/deliverable writing is omitted, host editing remains usable. Notices, publish status and transition guidance must explicitly say these edits are browser-local and unpublishable to GitHub; Commit cannot save them. A firmware-only commit must leave the remote host files untouched and must not clear local host recovery or its transition protection.

The operator also approved all five Phase 1 review resolutions in the handoff: explicit per-file legacy JSON adoption or DTS acceptance before creating a missing scoped JSON; a durable scoped-mode marker; retention of the last verified compatible host baseline on clean C-to-I/U Reload/reopen; firmware-only Create-branch carry under O/H=0; and keep-on-decline recovery limited to GitHub same-identity Reload/reopen. The JSON-choice prerequisite applies only when Commit would create or replace P's scoped JSON, never to proved legacy-mode writes. A valid choice selects only P's firmware JSON model; the ordinary snapshot matrix still governs host publication in the same Commit. The contracts and exact oracles below incorporate those resolutions.

These are approved target policies, not blanket shipped-behavior claims. Keep CAP-002/CAP-003 present-tense and update only behavior with executable evidence. Phase 1 resequenced the record; Phase 2 completed the bounded API/core and identity plumbing. Phase 3 still owns the full interaction.

## Acceptance criteria

- List eligible keymaps and let users select one within an authorized repository/branch. Explicit selection controls both load and commit; no fallback to the first file after selection disappears.
- Validate selected paths against the fetched tree/config inventory; reject traversal, templates and unauthorized files. Preserve head-SHA conflict protection and branch-race guards.
- Include keymap identity in drafts, host legend/snapshot ownership, reload, branch retargeting and publish. Reopening keymap B must not restore or commit keymap A data.
- Define backward-compatible ownership/migration for config/keymap.json, templates, physical-layout JSON, and host_keymap/snapshot.json before writing multiple keymaps. Do not silently attach one shared sidecar to every file.
- Single-keymap repositories retain a simple default. Missing/renamed files, no candidates, cancellation, failed writes and switching with dirty work have explicit safe outcomes.
- Implement the operator recovery policy above for both host-only and mixed firmware/host dirtiness. Prove Reload preserves recovery, confirmed host discard preserves firmware, and safe transitions work without a different GitHub destination or a misleading Commit/Reload exit.

### Proposed ownership and migration contract — review required

The safety policies are operator-approved targets for phases 2–3; concrete filesystem APIs still require the persistence ADR, and none is shipped behavior. They are derived from the inventory, not adopted from candidate conventions. Use `P` for the exact validated direct `config/<filename>.keymap` path; the filename, including case, is part of identity. GitHub identity is source + authorized repository + explicit branch + P. Installation remains an authorization context, head SHA a revision, and `keyboard` descriptive metadata rather than a substitute for P. No draft migrates automatically on rename, repository change or branch selection.

Inventory only eligible regular file entries immediately under `config/`, using core's user-keymap rule, with exact returned path/name agreement. Reject absolute paths, separators in the filename, dot/traversal segments, NUL, templates, unlisted paths and encoded attempts to bypass validation; decode transport once and validate, never normalize an unsafe selection into an allowed one. Do not follow links or select arbitrary nested files. Preserve exact path spelling through URL encoding. One candidate may default only when there is no prior explicit selection; multiple candidates require a choice; zero candidates or a vanished remembered path leaves the editor/recovery unchanged with a missing-selection notice.

Proposed deterministic scoped spelling for review: firmware cache `config/<full-keymap-filename>.json` (for example `config/a.keymap.json`); host root `host_keymap/keymaps/<full-keymap-filename>/` containing `snapshot.json`, `linux/<lang>.xkb`, `windows/<lang>.klc` and `windows/en-<lang>.klc`. Full filename avoids colliding with existing physical-layout `config/a.json`. These paths do not exist as a main-branch contract. The next persistence ADR must approve this spelling, mode detection and compatibility costs before any such write; until then multi-keymap writes are blocked.

### Acceptance matrix — proposed behavior, not executable evidence

Notation: `F` means unpublished firmware (including retained layer/source metadata); `H` means protected local host work, whether publishable or browser-local; `B` means an existing omitted-snapshot host-recovery block. Clean is `F=0,H=0`; firmware-only `1,0`; host-only `0,1`; mixed `1,1`. `C` = compatible supported owned snapshot; `I` = invalid or ownership/reference-incompatible snapshot; `U` = unsupported schema. `O` (omit remote host writes) is true for I/U. `B = O and H`; omission alone must not block a clean transition. H is not the current main `isHostRepoDirty` value and must remain recoverable across reopening, not be inferred from a publishability flag.

For C, compare the live snapshot to the captured immutable remote baseline. For I/U, use the last verified compatible host baseline for that same identity as the separately recorded local origin; use standard system English only when no verified baseline exists, never merely because the current remote snapshot is invalid, unsupported or ownership-incompatible. A C-clean session observing I/U on Reload/reopen retains that baseline and its tables locally with F=0,H=0,B=0,O=true: no automatic reset, synthetic host dirtiness or discard prerequisite. The retained origin is historical verified data, not proof that the current remote snapshot is compatible or writable. Preserve an already established local origin on repeated I/U loads, including a completed explicit D reset. A working-view/layout edit establishes H and durable pending recovery. Previously pending H stays pending on load, never becomes a new clean origin. O alone, stored assemblies alone and OS-install status do not establish H. Initial host persistence failure preserves usable live edits/H with a non-durable warning; reopening can recover only the last successfully stored revision, not edits the browser never stored.

`R` in every row means GitHub same-identity Reload as specified below: no discard, no recovery deletion or implicit publication. `T` means a destination can be attempted only after independent firmware protection and, for C/H, publication or verified identity-scoped retention. `D` means successful confirmed **Discard local host edits** under the transaction below. Tuple results assume no newer edit and successful verification; errors/races follow the rules after the table. All Commit results require proven ownership mode. Apply the explicit per-file JSON-choice prerequisite above only when Commit would create or replace P's scoped JSON; proved legacy writes need no such choice or path migration. A valid choice selects the firmware model only and does not override this snapshot matrix: compatible owned host work publishes with firmware in the same Commit, clearing only the sent host revision; host omission is limited to I/U, including ambiguous ownership. A failed prerequisite leaves F/H/B/O, live/stored work, all remote blobs and head unchanged. Reload/reopen never writes remote files; every table's unchanged-artifact assertions include other identities and global profiles.

### Explicit host-only recovery transaction

1. **Availability and scope.** D is a standalone source/chrome recovery action when B exists, including one repo/one branch/one keymap; a destination is not necessary. Before confirmation capture the current full identity, host recovery revision and exact owned records. The confirmation names repository, branch and P; says it removes this identity's browser-local host working view, owned edited layout copies, remembered assemblies and associated recovery/cache state; resets to system English; cannot save these edits to GitHub; and leaves firmware drafts/history and all remote files unchanged. Name any preserved global profiles separately. Cancel, Escape and closing the dialog make no state/storage/network changes. Consent to D is never firmware-discard consent.
2. **Replacement.** This confirmed D with B=true is an explicit reset, not the clean Reload/reopen origin-selection rule. I/U has no trustworthy current remote baseline to restore; a historical verified baseline may exist but must not override the confirmed reset. Use core `standardHostLegendView()` (`packages/keymap-core/src/host-legend-presets.ts:18-35,62-69`): one visible `en` / primary system English column, AltGr and AltGrShift on, `open: null`, no explicit keycap override; no identity-owned user working tables and no remembered assemblies. End the scoped host edit/decode session and clear its stale prompt/recovery references. Do not call this restored from GitHub or installed on the OS; OS-delivery status must describe the replacement, not falsely mark an install complete. Do not reset firmware layer-view preferences.
3. **Exactly removed/preserved.** Replace the selected identity's stored working view with the reset view, empty its assembly list, remove its private edited tables and pending recovery payload, and replace its dirty recovery state with a durable clean-reset revision. Invalidate outstanding writes for the prior revision. Keep O and its invalid/unsupported/ownership reason, remote identity/SHA provenance, and the reset revision so old legacy/global fallback cannot resurrect discarded work. Preserve every unrelated identity's settings/tables, global profiles, firmware baseline/live draft/history/undo/redo, stored firmware draft and layer metadata, source bytes, selection and head SHA. Never use `clearHostLayoutStore()` or bulk-reset the host registry. A shared/global table with uncertain ownership stays intact but is no longer referenced by this identity.
4. **Commit point and rollback.** Prepare replacement and ownership checks before mutation; fence concurrent host edits and queued persistence for the captured identity/revision. Cleanup, reset view/assemblies and revision must commit as one atomic host-storage transaction (the existing helpers do not provide that transaction). Do not mix firmware deletion into it. Abort/failure leaves the pre-discard live host state and stored recovery intact, B true, destination unapplied, and a retryable storage error; never announce success after swallowed storage errors. No best-effort deletion rollback that could erase a shared or newer row. If storage cannot establish atomicity/ownership, refuse D rather than silently discard. Host editing resumes usable on failure.
5. **After success.** Only after durable success apply the replacement in memory and clear H/B for the captured revision. O and the browser-local/unpublishable notice remain. Subsequent edits are usable and create new H/B; downloading host deliverables, firmware Commit, ordinary Reload or browser persistence does not clear them. On reopening, a completed reset restores standard view with no H/B; an aborted transaction restores the prior recovery/H/B. A crash between durable commit and UI update follows the durable revision on reopen. This is deletion of scoped recovery, not deletion or repair of the incompatible remote snapshot.
6. **Firmware and destination are separate.** Successful D in mixed state leaves firmware bit-for-bit intact and dirty. A requested switch must next publish F, or flush and verify F under its original identity, or obtain separate explicit firmware-discard confirmation. Failure to retain F blocks the switch without clearing the live draft. If destination loading fails after D has succeeded, remain on the original identity with reset host state and unchanged firmware; do not resurrect intentionally discarded host work or claim the switch succeeded. D's confirmation must make that separation clear.

### Reload, storage, stale work and transitions

- **GitHub same-keymap Reload is read-only with respect to protected work.** Capture identity and revision before fetch. Equal remote revision may refresh metadata, but retains live/stored firmware, layer/source metadata, host working tables/view/assemblies, recovery and dirty flags. If remote firmware/host changes while corresponding local work exists, keep the complete current session and its old publish base; report the remote change without silently merging, rebasing or deleting work. A refreshed head alone must not make an old draft safe to publish. Clean sessions may adopt a fully validated remote result atomically, except C-to-I/U retains the last verified compatible host baseline locally as origin with H=0,B=0,O=true, never resets or requires D. Failure/missing selected file leaves the session/recovery intact. For GitHub same-identity Reload/reopen only, declining restore keeps stored work rather than deleting it; a separately labeled destructive choice requires explicit confirmation. On live Reload keep the current draft; on reopen a deferred stored draft remains protected/unpublished under its original identity even if not applied to the view. Decline is not proof of F=0 or permission to overwrite the retained draft. Demo/Clipboard/Local keep their current decline-discards-firmware-draft semantics: remove the matching stored firmware draft and retain the loaded clean firmware baseline, without discarding host data or changing source files. Do not extend GitHub keep-on-decline to those sources without a separate approved CAP change.
- **Publish outcomes.** Capture P, branch/head, source/session generation and the exact sent firmware/host encodings. Successful write plus verified reload accepts only that sent baseline; later edits remain dirty/recoverable. I/U commit accepts firmware only; no host baseline or recovery is cleared and all remote host bytes remain unchanged. Stale head rejects before tree creation; non-fast-forward PATCH does not advance the branch. Tree/commit creation can leave unreachable objects but cannot justify success. Write success followed by failed/unverifiable reload keeps recovery and reports that remote files may already have changed; do not pretend to roll back GitHub or automatically retry the write.
- **Firmware retention is verified, not a warning-only best effort.** Await pending persistence and verify the original identity's complete draft and layer/source metadata at the captured revision before unloading it. If unavailable/quota/validation failure occurs, keep the session and refuse the switch. Compatible host work can likewise be retained as an identity-scoped working snapshot plus immutable remote baseline; reopening overlays that recovery only on its matching provenance. A changed baseline preserves the recovery separately and requires reconciliation, never silent deletion. Storage success is not publication. Firmware persistence and host cleanup use different databases today; do not claim cross-database atomicity.
- **Stale work.** Loads, confirmation results, commits, host writes, draft flushes and cleanup completions must be bound to full identity plus session/recovery revision. Newer edits invalidate an open destructive confirmation; require a fresh confirmation. Old callbacks must not mutate current selection, baseline, dirty flags, notices, saving locks or another identity's rows. Persistence needs a transaction-time revision check/serialization, including competing tabs; a generation check after an awaited write is insufficient. A completed publish for an old session may have changed its remote target, but cannot clear current recovery. A committed D remains committed even if its UI callback is stale; never apply its reset to the newer identity.
- **Recovery on GitHub reopen.** Retain F and H independently; reopen A cannot restore B even if keyboard name/layout are identical. In I/U restore A's H/O/B before permitting a source change; do not recapture mutable H as a clean baseline. If C was clean and the current result is I/U, recover A's last verified compatible baseline/view/tables as local origin with H=0,B=0,O=true and no D prerequisite; standard English is only the fallback with no verified baseline, subject to an already completed explicit reset revision. Unreadable recovery/storage is an explicit error, not proof that no baseline exists or that state is clean; retain live work and refuse a destructive transition until safety can be established. For a newly observed C snapshot after prior I/U, preserve outstanding local H and reconcile ownership/baseline before publishing; merely observing compatibility does not erase recovery. After verified compatible publication, H/B are cleared for the sent revision and no host discard is required.

### ADR implications and remaining review boundaries

- **A persistence ADR change is required before implementation writes.** ADR 0002 currently makes shared `keymap.json` primary and describes template priority; selected-file JSON ownership, explicit per-file legacy adoption or DTS acceptance bounded to Commit creating/replacing P's scoped JSON, matching-template rules and durable marker-based mode proof need a durable extension. Proved legacy sole-keymap writes retain their existing paths without a JSON-choice prompt, marker or scoped minting. The marker must outlive scoped data deletion; unknown mode refuses Commit rather than legacy fallback. Preserve core serializer/splice/validation and Clipboard/Local paths. ADR 0005 fixes shared host paths, remote-load priority and combined Commit; scoped ownership, I/U omission, retained last verified compatible baseline as a clean local origin, firmware-only O/H=0 branch carry without host recovery, recovery overlays and explicit host-only reset need an exception/extension. JSON choice selects only the firmware model, not a host-publication exception: compatible owned host work publishes in the same Commit, only the sent host revision clears, and omission is limited to I/U, including ambiguous ownership. GitHub same-identity keep-on-decline is a bounded future CAP-002 recovery change, not a change to Demo/Clipboard/Local decline-discard behavior. Keep accepted ADR identities; use the next indexed decision or amendments according to review, not a fabricated already-accepted ADR. ADRs/index are intentionally not edited here.
- The five safety resolutions are operator-approved; independent review still must verify their complete specification and approve the concrete scoped spelling, marker path/schema/initialization proof, consent/provenance representation and global-profile isolation strategy before implementation. Implicit shared-sidecar assignment, reverse migration by manual marker removal, automatic renames and remote conflict merging are unsupported. Deleting scoped data while retaining the marker is explicitly covered and never causes legacy fallback. Refuse unsafe writes/rebinding and preserve data; implementation details are not permission to weaken the approved rules.
- Wire-level inventory/selection/error field names and storage schema/transaction implementation remain phase-2 design details, constrained by the exact behavioral oracles above. In particular the existing per-row helpers and swallowed storage errors are insufficient to prove atomic host discard or verified retention. If implementation cannot meet those guarantees, return to this active CHG for a reviewed prerequisite; do not weaken recovery or retrofit candidate completion claims.
