# ZMK layout discovery fixture contract

Specification-only evidence for [CHG-008](../../../../docs/changes/active/CHG-008-discover-layouts-from-zmk-metadata.md). Nothing here implements discovery or expands CAP-001/CAP-002. The CHG owns phase state and review gates; this file owns test inputs and proposed acceptance, not a parallel execution plan.

## Location and existing seams

Core owns fixture data and shared file contracts. This directory follows the existing core fixture/specification precedent without creating a CHG review package (which would require an owner link), a product proposal screen or a new runtime architecture decision. All names and metadata in the fixtures are synthetic, authored for this repository under its MIT license; they are not copied board designs or a supported-keyboard list.

Read these current seams before implementing the proposed outcomes:

- `src/keyboard-bundle.ts`: `loadKeyboardBundle` picks supplied nonempty layouts, otherwise infers from layer zero. `pickInfoLayout` chooses `default` then first, or an explicitly requested layout name. Neither is a discovery API.
- `src/layout.ts`: `inferRectangularLayout` is the fallback; `renderTable` sorts by `row`/`col`. `validateInfoJson` alone does not establish count, duplicate-cell or finite-geometry safety.
- `src/dts-splice.ts`: `assertLayerKeyCounts` checks every layer. A no-op splice can preserve original binding bytes and conceal a dangerous serialization-order change; test an actual edit as well as a no-op.
- `apps/api/src/services/github/files.ts`: pinned selected-file ownership and `fetchInfoJson`; GitHub legacy uses `config/info.json`, then safe matching `<stem>.json`; scoped uses only matching geometry. Reserved `info`/`keymap` stems are not alternative geometry. Firmware `keymap.json` priority is a different contract.
- `apps/web/src/lib/clipboard/load.ts`: supplied layout is parsed before bundle loading; malformed supplied JSON and count mismatch are errors. `apps/web/src/lib/github/api.svelte.ts` consumes the bundle; the API does not currently discover geometry.
- Local still requires metadata, per CAP-002. Do not turn the shared helper's fallback into a claim that every adapter already supports it. Filesystem's separate read-only geometry and one-file save boundary stay unchanged.

Paths above are repository-relative except `src/`, which is relative to `packages/keymap-core/`. Existing evidence: `keyboard-bundle.test.ts`, `layout.test.ts`, `dts-sensors.test.ts`, API `files.test.ts`/`selected-files.test.ts`, and web `clipboard/load.test.ts`.

## Proposed initial subset

The initial syntax contract is **closed, static, literal metadata**, not general Zephyr compilation:

1. Unibody transforms and split keyboards whose variants share one complete logical-position map. A split entry names its parts, each part's declared local scan extent and transform offsets. Do not concatenate independently discovered halves, guess mirrored wiring or synthesize missing keys.
2. One resolved `zmk,matrix-transform` node with positive literal `rows`/`columns`, optional literal nonnegative `row-offset`/`col-offset`, and `map = <RC(row, col) ...>;`. Map array index is binding index. Sparse maps are allowed; holes are not additional keys, and `&none`/`&trans` bindings still count.
3. Recognize exactly `zmk,matrix-transform` and `zmk,matrix_transform` as discovery compatible aliases. Preserve the original token in provenance. The hyphen spelling is canonical in the pinned ZMK binding; accepting the underscore spelling is an editor compatibility policy, NOT certification that either compiles in every ZMK version. Likewise accept either spelling of the chosen property; if both exist they must reference the same node. No fuzzy spelling normalization.
4. Optionally one selected `zmk,physical-layout` with a resolved `transform` phandle and `keys` entries of exactly seven literal cells after `&key_physical_attrs`: width, height, x, y, rotation, rotation-x, rotation-y. Require its locally supplied/pinned `zmk,key-physical-attrs` declaration with `#key-cells = <7>`. The cells use hundredths of a key unit / degree. Convert width to `LayoutKey.w` for current consumers and layout JSON export, retaining the same width in `u` for the existing contract; height maps to `h`, and x/y/r/rx/ry to their corresponding fields. `ComboDictionary.svelte` reads only `w`, while `Keyboard.svelte`, `matrix-scheme.ts` and `combo-arcs.ts` prefer `u`; `validateInfoJson` checks `u` but does not validate `w`. Require both width fields to be equal, finite and positive, and prove their retention through bundle load and layout JSON round-trip rather than treating that validator alone as sufficient. Require positive height, nonnegative x/y, finite signed-16-bit-range values, and exact key count. A missing `keys` property permits transform-only inference; malformed/present keys do not silently downgrade to transform-only geometry.
5. One optional `zmk,keymap-sensors` node with a required `sensors` property listing unique, resolved, enabled sensor labels in source order. An absent node is valid metadata with no verified sensor association: retain otherwise valid candidate geometry, not rectangular fallback. A present node without that property is invalid metadata, not absence, and discards the candidate. Both outcomes retain raw firmware sensor bindings. The initial hardware subset is `alps,ec11`; it supplies slot identity, not GPIO validation, encoder direction inversion or physical placement. No fabrication of sensor slots, press keys or hardware.

Initial production inventory is deliberately a finite, reviewed allowlist at the pinned upstream revision, not “all ZMK boards” or the Demo catalog. This phase supplies only synthetic entries (`spec_unibody`, `spec_split`, `spec_physical`) to specify that subset; it vendors no real-board catalog. Before a real entry can be shipped it must carry the source manifest and closure proof below. Unsupported boards remain usable through the existing fallback. New syntax, new source families or more permissive limits require separate reviewed fixtures before inclusion.

### Expressions, includes and resource limits

- Accept decimal integer literals, whitespace/comments, fixed `RC(decimal, decimal)` cells and bare label phandles (`&label` or `<&label>` for single-reference properties). For physical rotation/origin cells only, also accept a parenthesized negative decimal literal such as `(-1500)`; this is not a general expression evaluator.
- No hex/packed RC integers, arithmetic, bitwise expressions, symbols in numeric cells, macro expansion, `#if`, function macros, DTS delete directives, arbitrary overlay merge order, aliases that change metadata, position-map remapping, runtime ZMK Studio layout selection or generated scan maps. Unknown constructs that can affect the selected closure yield unsupported, not a partially parsed success. Known unrelated hardware/behavior properties may remain opaque only when the entry's reviewed closure proves they cannot affect layout resolution.
- Runtime discovery consumes bundled, pre-resolved metadata plus the selected document's bounded selector/override information. It never invokes `cpp`, `dtc`, CMake, west or a shell. Raw user includes are not read, fetched or followed, even when relative and apparently harmless. An unresolved include that might define/override metadata makes discovery unsupported. Existing firmware parsing/preamble preservation is not permission to expand metadata includes.
- The exact stock `#include <behaviors.dtsi>` and `#include <dt-bindings/zmk/keys.h>` lines in `bindings.keymap` are allowed non-metadata preamble for the reviewed stock definitions, not metadata inputs. Preserve them without following them. This is not a blanket allowance for angle-bracket includes, `.dtsi` files or a same-named user replacement: stock identity and non-metadata effect belong to the pinned closure proof. Inspect includes in the selected keymap as well as the metadata input. Any include that can declare or override metadata, including a quoted overlay such as `#include "unresolved-layout.dtsi"`, makes discovery unsupported unless its exact source and effect are already covered by the manifest's proved bounded, pre-resolved closure. Never obtain that proof by following a raw user include at runtime. The positive `unibody` case retains the stock preamble; `keymap-metadata-include` adds only that quoted include and must fall back without I/O.
- Maintenance may resolve only an enumerated dependency list from one pinned local upstream checkout. Every input and exact include edge is in the manifest; reject missing edges, cycles, escapes, symlinks and conditional dependencies. This is finite offline curation, not recursive include discovery. An already-resolved literal metadata snapshot is the runtime artifact.
- Proposed per-entry limits: 32 source files, include depth 8, 256 KiB total UTF-8 source, 64 candidate layout/transform nodes, 512 keys, 16 sensors, and matrix dimensions 1–255 with offsets/RC cells 0–254 and checked in-range sums. The runtime resolved document also has the 256 KiB limit. Detect excess before allocating a matrix or expanding input; return unsupported with a limit explanation. These are editor safety limits, not claims about all valid ZMK firmware.

## Resolution, precedence and failure contract

1. Keep accepted source identity: GitHub repository/branch/exact keymap path/pinned head, or the existing Clipboard/other document revision. Board metadata never replaces source/draft identity or expands file ownership.
2. Explicit layout JSON wins, using each adapter's current matching/path rules above. Do not inspect discovery to replace supplied geometry or silently fix invalid explicit geometry. Supplied JSON parse/validation/count failures remain actionable errors; leave the accepted document unchanged. Core's existing `{ layouts: {} }` compatibility fallback is not proof that malformed explicit JSON is safe or absent in stricter adapters. Do not broaden or remove that behavior in this phase.
3. Without explicit geometry, obtain an exact catalog board/revision and optional shield/part selection from an explicit user choice. A controller board is not sufficient to guess its shield. Filename, display name, key count, repository name and Demo ID are hints at most. No new build-YAML/Kconfig discovery. A remembered metadata choice is scoped to the source revision and catalog revision; revalidate it after either changes.
4. Resolve the selected document's bounded chosen reference against that entry. A chosen matrix transform takes precedence over physical-layout selection, matching the pinned firmware; do not attach ignored physical keys from another node. If no matrix chosen exists, use chosen physical layout and its transform. If there is no chosen selector, one eligible layout (or one transform when there are no physical layouts) can be offered; multiple candidates require an explicit preview choice, never first-object order. An explicit stale/missing/disabled reference is an error reason, not permission to choose the sole remaining node. Duplicate labels, conflicting spellings/references and unproved override order are ambiguous. A user choice may disambiguate eligible unchosen candidates; it cannot override conflicting firmware chosen declarations without a corrected source/reload.
5. Recognize only a selected transform's literal offset override from the selected variant/document when its origin and order are proved. Multiple conflicting assignments or arbitrary map/dimension overrides are unsupported. If firmware selection disagrees with the requested preview, report the conflict; do not edit chosen properties or silently remap bindings.
6. Validate every layer against the map length, not only layer zero; require a nonempty keymap and no dropped, padded or reordered keys. Bad discovered count discards the candidate and uses the unchanged rectangular fallback if all layers can safely use it. Inconsistent layer lengths/empty keymaps give an actionable error and preserve the live document, not a truncated fallback.
7. Unknown board, absent metadata, unresolvable/ambiguous selection, unsupported syntax/limits and invalid metadata produce distinct explanatory reasons and a safe binding-count rectangle where possible. Offer correction or explicit layout input; do not show a candidate as accepted. No silent partial success, hidden keys, inferred `absent` slots or loss of existing sensor bindings. Transport/access failures reading owned explicit inputs remain load errors, not “metadata absent.”

### Positions, offsets, order and sensors

- Validate integer RC coordinates, declared extents, uniqueness and index identity before normalization. Matrix `map[i]` gives the global scan coordinate for logical binding i. Array order is authoritative, not coordinate sorting or source line breaks.
- Transform offsets apply to **local scan events before lookup**, not to every map cell. Do not add a right-half offset to an already global full map, and do not concatenate the same full map twice. For each split part, map local `(r,c)` to global `(r + row-offset, c + col-offset)`, prove the result is in bounds and corresponds to exactly one logical slot. Declared populated local positions (not every unused scan hole) must cover the global map exactly once across parts; overlaps, holes and conflicting part maps invalidate the candidate. Scan dimensions/populated positions come from the curated entry, not guessed GPIO counts.
- Preserve electrical RCs and offsets separately in discovery provenance. For generated `LayoutKey[]`, assign stable writer coordinates in binding order using the existing `inferRectangularLayout(N)` row/column slots; set x/y from the global RCs for transform-only display. Physical-layout keys instead supply x/y/w/u/h/r/rx/ry by the same logical index, with identical `w` and `u` widths. Never use an unsorted electrical map as writer row/col. Scheme must describe these as serialization slots, not measured wiring; presenting electrical RCs later needs separate metadata, not overloaded fields.
- A transform-only rendering is an **inferred electrical arrangement, not measured physical geometry**: no guessed stagger, split gap, rotation, handedness or key size. Physical metadata is source-declared geometry, not independently measured/verified hardware. Exact duplicate physical origins are rejected in the initial subset; overlap detection for rotated key shapes is not claimed. All numeric output must be finite.
- Sensor count is separate from map length. For a declared supported sensor list, require each nonempty layer `sensor-bindings` list to match its length and preserve list index as sensor identity; an absent/empty per-layer list means no assignment, not deleted hardware. Duplicate/unresolved/disabled labels, unsupported sensor kinds or conflicting counts invalidate discovered metadata. An absent optional sensor node leaves otherwise valid discovered geometry as a candidate with no declared sensor labels and an unverified association; it does not trigger rectangular fallback. A present node missing its required `sensors` property is malformed metadata: discard the candidate and use the safe rectangle where possible. Retain raw firmware sensor slots in both cases; never infer association from standalone encoder declarations, guess a matrix key or drop a slot. An encoder press is already an ordinary key when present in the map.

## Acceptance and export boundary (future interaction)

Discovery can produce a preview, not a layout-file write. Preview names exact board/shield/variant, source/catalog revisions, selected transform/layout, inferred versus declared geometry, sensor association and fallback reason. Accept is an explicit action captured against the same document, bindings, source head and catalog version; cancellation or stale selection must preserve the live layout, draft and history. Never re-layout accepted work automatically after catalog refresh/reload. Explicit JSON remains authoritative even when discovery is available.

A separate explicit export action may download/copy generated layout JSON after validation and an order-preserving export/re-import check. It is not Copy .keymap or GitHub Commit, not acceptance of firmware/host publication, and not permission to overwrite any existing JSON. No automatic GitHub geometry/sidecar write, Filesystem multi-file save, source/chosen rewrite or host change. Ordinary firmware saves retain ADR 0002/0005 ownership and splice rules. Filesystem integration is optional later work, not part of this specification's implementation.

Mutations are test-data recipes, not DTS parsing. `metadata: null` means genuinely absent metadata. `bindings` overrides are explicit lists for count cases. Matrix IDs below correspond to case IDs where provided.

### What the executable evidence actually proves

`../../src/layout-discovery-boundary.test.ts` checks that exact mutation recipes apply once, all fixture keymap lists parse, and expected successful fixture positions/part events are internally consistent. Those checks validate test data, NOT metadata discovery.

It also calls existing production seams to prove:

- explicit hand-authored geometry is retained (including the absent-sensor-node candidate); withholding geometry for missing or malformed metadata yields the existing rectangle/warning, and both paths preserve firmware sensor slots. These tests supply or withhold geometry themselves, not through metadata discovery;
- the hand-authored physical width reaches both `w: 1.25` and `u: 1.25` through existing bundle loading and layout JSON serialization/reload (not metadata parsing or an implemented discovery export action);
- invalid supplied nonempty geometry errors rather than silently using the rectangle;
- the proposed hand-authored normalized layout can make a real edited source-preserving write, retaining logical order and sensor bindings in DTS and JSON;
- using raw non-row-major electrical RCs as writer row/col actually reorders an edited export today (a passing characterization of the hazard, not an accepted discovery implementation);
- all-layer count checks still refuse mismatch.

The existing API and web focused suites additionally protect current matching JSON and safe fallback behavior. No new test uses `it.fails`, skipped tests or a fabricated discovery API. The remaining table rows require real Phase 2/3 implementations and regressions before they can be called passing acceptance. Independent review of this contract/matrix remains the orchestrator's gate.
